### P1 — 정확성·안정성 (먼저 처리)
1. **PTY 세션 프로세스 누수 (타임아웃 후 자식 프로세스 잔존)** — `apps/server/src/pty-manager.ts:155-158`
   `proc.kill()` 은 PTY 리더에만 SIGHUP 을 보낸다. `claude-stream.mjs` 가 띄운 하위 프로세스(검사 명령 등)가 남을 수 있다. 종료 후 프로세스 그룹 kill 또는 SIGKILL 에스컬레이션 타이머 필요. `killAll()`(246행)도 동일.
2. **`command()` 중 서버 크래시/재시작 시 워킹 트리 오염 복구 불가** — `apps/server/src/orchestrator.ts:229-284`
   `phase`·`work`(baseline)가 메모리에만 있다. 작업 도중 서버가 죽으면 baseline sha 를 잃어 승인/반려가 불가능하다. `.data/state.json` 에 `{commandId, baseline sha, untracked}` 를 `runTask` 시작 시점(287-288행)에 같이 저장하고 기동 시 복구하거나 최소한 경고.
3. **`decide()` 반려 시 `checkout baseline.sha` 가 사용자의 동시 편집을 덮어씀** — `orchestrator.ts:418-421`
   에이전트 실행 중 사용자가 같은 파일을 수정하면 baseline 으로 되돌리며 그 수정이 사라진다. 반려 전 해당 파일의 현재 내용이 에이전트 diff 와 일치하는지(해시) 확인하거나 `.data/rejected` 보관에 "되돌리기 직전 전체 파일"까지 저장.
4. **`revertProject` 의 `.then(() => existsSync && unlinkSync)` 체인에서 rm 실패 무시** — `orchestrator.ts:420`
   `git rm` 결과 코드를 확인하지 않고 파일을 삭제한다. 가독성도 나쁘다 → 단계별 if 로 분리하고 실패는 `log` 에 남긴다.
5. **WebSocket 입력 검증 부족** — `apps/server/src/index.ts:89-94`
   `pty:input` 은 길이 제한 없이 `String(msg.data)` 를 PTY 에 쓴다(로컬 전용이지만 `PIXELBOSS_HOST` 설정 시 `verifyClient` 가 origin 검사를 건너뜀, 55행). 비로컬 바인드 시 인증 토큰이 없는 상태에서 `project:add`/`pty:input` 이 모두 열린다 → 비로컬 호스트에서는 토큰 필수화 또는 `pty:input`/`fs:list`/`project:add` 비활성화. `ws` `maxPayload` 도 명시 권장.
6. **`state.json` 파싱 실패 시 서버 기동 불가** — `orchestrator.ts:59`
   `JSON.parse` 가 try 없이 생성자에서 실행된다. 손상된 파일 하나로 백엔드가 뜨지 않는다 → try/catch 후 백업 파일로 이름 변경하고 기본값 사용. `saveState`(98행)도 임시 파일 + rename 으로 원자적 쓰기 권장.

### P2 — 성능 병목
1. **PTY 출력이 청크마다 전체 소켓 JSON 직렬화** — `index.ts:24-31`, `orchestrator.ts:66`
   `pty:data` 는 구독자가 없어도 매 청크마다 `JSON.stringify` 를 수행한다(raw 를 구독 확인 전에 생성). 구독자가 있을 때만 직렬화하고, 16~50ms 단위로 청크를 합쳐 전송(배칭)하면 6세션 동시 출력 시 프레임·CPU 부담이 크게 줄어든다.
2. **`append` 의 문자열 재할당** — `pty-manager.ts:91-95`
   `history += data` 후 256KB 초과 시마다 `slice` 로 새 문자열을 만든다(출력이 많으면 청크마다 256KB 복사). 청크 배열(링 버퍼)로 보관하고 필요할 때만 join 하거나, 초과분이 커졌을 때 한 번에 자르는 방식으로 변경.
3. **idle 감지가 매 청크마다 `stripAnsi(s.history)` 전체 처리** — `pty-manager.ts:150`
   1.2초 타이머가 만료될 때마다 최대 256KB 에 정규식을 돌린다. 마지막 ~512자만 잘라서 처리하면 충분.
4. **`detectDelta` 가 변경이 있으면 전체 `git diff HEAD` 를 읽어 해시** — `git.ts:107`
   5분 주기 스캔마다 프로젝트 6개의 전체 diff 를 메모리에 올린다(maxBuffer 20MB). `git status --porcelain` + 변경 파일 mtime/size 또는 `git diff HEAD --stat` 로 핑거프린트를 만들면 대형 diff 에서 크게 빨라진다.
5. **`diffSinceBaseline` 의 신규 파일별 `git diff --no-index` 직렬 실행** — `git.ts:167-170`
   파일마다 프로세스 1개씩 순차 실행. `Promise.all` 로 병렬화하거나(상한 4~8) 합계 200KB 초과 시 중단. `diff` 문자열 합친 뒤 자르는 순서(176행)도 먼저 누적 상한을 두는 편이 메모리상 유리.
6. **`takeBaseline` 이 같은 프로젝트의 부서 태스크마다 호출됨** — `orchestrator.ts:287`
   직렬 실행이라 정확성에는 문제 없으나(두 번째 baseline 이 첫 부서 변경을 포함 → `this.work` 에는 첫 baseline 만 유지, 288행), 부서별 diff 가 서로 겹쳐 `files`/`diff` 가 누적 표시되는 구조다. 부서 단위 귀속이 목적이라면 `ProjectReport.files` 를 직전 diff 와의 차집합으로 계산해야 정확하다.
7. **렌더 루프 상시 60fps + 그림자 2048 맵** — `apps/web/app/utils/voxel/engine.ts:52-53,86,270-285`
   `requestAnimationFrame` 이 탭이 숨겨져도(브라우저가 스로틀하긴 함) 항상 `render` 한다. 24시간 대시보드 용도이므로 `idle` 상태에서 15~30fps 로 낮추고, 변경 없을 때 그림자 `autoUpdate=false`/`needsUpdate` 수동 갱신을 검토. `visibilitychange` 로 루프 정지도 추가.
8. **캐릭터 파츠마다 Material 신규 생성** — `apps/web/app/utils/voxel/character.ts:96`
   `mk()` 마다 `new MeshLambertMaterial` 이라 캐릭터 1명당 수십 개 → 7명×부서 수 만큼 머티리얼·드로우콜이 늘어난다. 같은 색은 `world.ts` 의 `mat()` 캐시(20행)를 재사용하도록 변경(상태 색 변경용 `materials` 배열은 필요한 파츠만 개별 복제).
9. **`setProjects` 가 프로젝트 변경 시 오피스 전체 재구성** — `engine.ts:139-150`
   프로젝트 추가/삭제마다 `rebuildOffice` + 캐릭터 전체 교체. 지오메트리 `dispose` 는 `engine.ts:180-184` 에서 처리되나 `boxGeo` 캐시(world.ts:13)는 공유라 dispose 하면 캐시와 불일치 위험 → 캐시 지오메트리는 dispose 대상에서 제외하는지 확인 필요.
